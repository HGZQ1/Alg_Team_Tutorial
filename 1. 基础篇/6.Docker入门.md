# 第6章 Docker入门

这一章要解决的是一件听起来不像技术问题的技术问题：**怎么让你写好的程序，在别人的电脑上、在机器人的板子上，也能一模一样地跑起来。**

听起来像是个不值得单开一章的小事，但相信我，这是算法组每年消耗时间最多的事情之一。你会遇到这样的场景：代码在你笔记本上跑得好好的，拷到机器人上就报错；队友重装了系统，花两天才把环境配回来；比赛前一天换了台电脑，`import torch` 直接崩了。

Docker 就是用来终结这类问题的。

这一章会有不少新概念和一堆命令，但它们之间的逻辑其实很清楚。我们会先把三个核心概念讲透，再回过头逐行读我们真机上用的配置文件。**看不懂的地方先跳过，把命令敲一遍看看发生了什么，比盯着文字想半天有用得多。**

本章出现的每一条指令、命令和配置字段，在 **6.13 速查表**里都有一句话解释和典型写法。看正文时遇到不认识的名字，翻到那边对一下就行，不用记。

最后有一句话要说在前面。这一章用来当例子的 Dockerfile 和 compose 文件是**我自己写的**，一边睡觉一边堆出来的，里面有明摆着的冗余、写了没用的变量、改完忘了同步的注释。会在正文里直接说"这块是写烂了、当时为什么会写成这样"。

这么做有两个原因：一是你们迟早要读到这些文件，与其自己对着犯迷糊，不如我先招了；二是我希望你们知道，能跑的工程代码本来就长这样，看到不完美的地方不用怀疑自己读错了。**照着学思路，别照着抄毛病。**

## 本章学习目标

完成本章后，你应当能够：

- 说清楚 Docker 解决的是什么问题，以及它和虚拟机的区别；
- 分清**镜像**、**容器**、**Dockerfile** 三者的关系，并能用做菜的类比向别人解释；
- 在 Ubuntu 22.04 上装好 Docker 和 NVIDIA 容器运行时，并让普通用户免 `sudo` 使用；
- 用 `docker run` 起一个容器，理解为什么容器退出后数据会丢失；
- 读懂一份 Dockerfile，说明 `FROM`、`RUN`、`COPY`、`ENV`、`ARG`、`USER`、`CMD` 各自在做什么；
- 解释为什么多条 `apt-get install` 要用 `&&` 串成一条，以及镜像分层缓存的意义；
- 读懂一份 `docker-compose.yml`，说明挂载、设备映射、网络模式和 GPU 相关配置的作用；
- 用 `.env` 文件把可变参数从配置里抽出来；
- 走通"构建 → 启动 → 进入容器 → 改代码 → 关闭"的日常工作流，并知道什么时候需要重新构建；
- 把构建好的镜像导出、切分、传给队友并还原；
- 说明镜像分层继承（`FROM 本地镜像`）为什么不会让硬盘占用翻倍，以及我们为什么**没有**采用分层架构。

本章环境基线是 **Ubuntu 22.04**。Docker 在 Windows 和 macOS 上也能用，但涉及相机、串口、GPU 的部分会有额外的麻烦，我们组统一在 Ubuntu 上做。

## 6.1 我们到底在解决什么问题

### 6.1.1 三个真实场景

**场景一：版本地狱。**
ROS2 Humble 官方只支持 Ubuntu 22.04。你的电脑装的是 24.04，硬装会遇到一堆依赖冲突。而你要用的某个 YOLO 库又要求 `numpy < 2.0`，系统自带的却是 2.x。你把 numpy 降级了，结果另一个包又炸了。

**场景二：换机器。**
你花了一周把环境调通，队友拿到代码，照着你的笔记装了一遍，还是跑不起来——因为你忘了记录中间某个 `apt install`，或者你的显卡是 40 系而他是 50 系，PyTorch 版本不一样。

**场景三：赛场突发情况。**
比赛现场网络又慢又不稳，你需要在半小时内把环境部署到一台新机器上。如果这时候还要联网 `pip install`，基本就废了。

这三件事的本质是同一件：**"环境"这个东西太脆弱、太难复制了**。它散落在系统的各个角落——apt 装的包、pip 装的包、环境变量、编译好的动态库、udev 规则——任何一处对不上，程序就跑不起来。

### 6.1.2 Docker 的思路

Docker 的做法很朴素：**把整个环境打包成一个文件，连同你的程序一起搬走。**

打包出来的东西叫**镜像（Image）**。它里面有一个完整的 Ubuntu 22.04 文件系统，装好了 ROS2、CUDA、OpenCV、PyTorch、你需要的一切。你把这个镜像拷到任何一台装了 Docker 的机器上，跑起来的环境和你调试时一模一样。

### 6.1.3 和虚拟机有什么区别

很多人第一反应是"这不就是虚拟机吗"。有关系，但不一样：

```text
        虚拟机                              Docker 容器

  ┌──────┐ ┌──────┐                   ┌──────┐ ┌──────┐
  │ App  │ │ App  │                   │ App  │ │ App  │
  ├──────┤ ├──────┤                   ├──────┤ ├──────┤
  │ 依赖 │ │ 依赖 │                   │ 依赖 │ │ 依赖 │
  ├──────┤ ├──────┤                   └──────┘ └──────┘
  │完整的│ │完整的│                        ↓        ↓
  │操作  │ │操作  │  ← 每个都要一整套   ┌──────────────┐
  │系统  │ │系统  │     几十 GB          │ Docker 引擎  │
  ├──────┴─┴──────┤                   ├──────────────┤
  │   虚拟机管理层  │                   │  宿主机内核   │ ← 共用同一个
  ├───────────────┤                   ├──────────────┤
  │   宿主机系统    │                   │  宿主机系统   │
  └───────────────┘                   └──────────────┘

  启动要几分钟                          启动只要几秒
  几十 GB                              几百 MB ~ 几 GB
  性能有损耗                            几乎没有损耗
```

关键差别是：**虚拟机自己带一个完整的内核，Docker 容器直接借用宿主机的内核。**

这带来两个后果，一好一坏：

- 好处是**轻**。容器启动只要几秒，性能几乎没损耗，对我们跑视觉算法很重要。
- 坏处是**不能跨内核**。Linux 容器只能跑在 Linux 内核上。在 Windows 上用 Docker，其实底下还是偷偷开了个 Linux 虚拟机。

对我们来说好处远大于坏处，因为机器人上跑的本来就是 Linux。

> 顺便解答一个常见疑问：既然共用内核，为什么 Ubuntu 24.04 的宿主机上能跑 Ubuntu 22.04 的容器？因为发行版的差别主要在**用户空间**（各种库和工具），内核接口是向后兼容的。容器带的是 22.04 的那套库，内核用宿主机的，所以能跑。

## 6.2 三个核心概念

这一节是整章的地基，务必搞清楚。

### 6.2.1 做菜类比

| Docker 概念 | 类比 | 说明 |
| --- | --- | --- |
| **Dockerfile** | 菜谱 | 一个纯文本文件，一步步写清楚怎么做 |
| **镜像 Image** | 做好的预制菜（冷冻的） | 按菜谱做出来的成品，可以复制、可以搬运，本身是只读的 |
| **容器 Container** | 端上桌正在吃的那一盘 | 把预制菜热一下就成了容器。可以有很多盘，吃完就扔 |

三者的关系：

```text
   Dockerfile  ──── docker build ────▶   镜像 Image
   （文本菜谱）                          （只读的成品）
                                             │
                                    docker run│（可以跑很多次）
                                             ▼
                                    ┌────────┼────────┐
                                    ▼        ▼        ▼
                                 容器1    容器2    容器3
                                （可读写，互相隔离，随时可删）
```

几个要点：

- **一个镜像可以起很多个容器**，互不影响。就像一份预制菜配方可以做出很多盘。
- **镜像是只读的**。容器运行时的所有修改，都写在一个额外的"可写层"里，不会影响镜像本身。
- **容器默认是一次性的**。删掉容器，里面的修改就没了，镜像还在。

### 6.2.2 容器是一次性的，这很重要

新手最容易掉进的坑是这个：进容器里 `pip install` 装了个包，改了几个配置文件，然后 `exit` 退出、删掉容器——**所有修改全部消失**。

这不是 bug，是设计。容器被有意做成"用完即弃"的，好处是每次启动都是干净一致的状态，不会积累出一堆说不清的脏东西。

那我们改的代码怎么办？两条路：

1. **改 Dockerfile 再重新构建**——适合环境层面的东西（装了个新库、改了环境变量）；
2. **挂载（volume）**——把宿主机的文件夹映射进容器，容器里改的其实是宿主机的文件，退出也不会丢。适合我们天天在改的代码。

我们真机配置用的就是第二条路：

```yaml
volumes:
  - ../:/ros2_vision_project
```

这一行的意思是：把宿主机上项目根目录（`..`），映射到容器里的 `/ros2_vision_project`。你在宿主机上用 VS Code 改代码，容器里立刻就能看到；容器删了代码也还在。

```text
      宿主机                             容器内

  ~/rc2026_vision/          ←──映射──→   /ros2_vision_project/
      ├── src/                               ├── src/
      ├── docker/                            ├── docker/
      └── models/                            └── models/

      用 VS Code 改这里             ──▶     这里立刻同步
```

**这是 Docker 开发流程里最关键的一个设定**，理解了它，后面就顺了。

### 6.2.3 镜像是一层一层叠出来的

再讲一个概念，它能解释很多"为什么 Dockerfile 要这么写"。

镜像不是一个整块的文件，而是**很多层（layer）叠起来的**。Dockerfile 里每一条 `RUN`、`COPY`、`ENV` 都会产生新的一层：

```text
   ┌───────────────────────────┐  ← 第 9 层：CMD ["/bin/bash"]
   ├───────────────────────────┤  ← 第 8 层：创建 developer 用户
   ├───────────────────────────┤  ← 第 7 层：pip 装 PyTorch
   ├───────────────────────────┤  ← 第 6 层：编译 librealsense
   ├───────────────────────────┤  ← 第 5 层：apt 装 ROS2
   ├───────────────────────────┤  ← 第 4 层：apt 装 CUDA
   ├───────────────────────────┤  ← 第 3 层：apt 装编译工具
   ├───────────────────────────┤  ← 第 2 层：换 apt 源
   └───────────────────────────┘  ← 第 1 层：FROM ubuntu:22.04
```

这个设计带来两件很实用的事：

**第一，构建有缓存。** 重新构建时，Docker 会从上往下检查每一层有没有变化。没变的直接复用，从**第一个变化的地方**开始重新执行。

所以 Dockerfile 的顺序很讲究：**越不容易变的东西写在越前面**。我们的 Dockerfile 把 apt 换源、装系统工具放在最前，把 `requirements.txt` 放在很后面，就是这个道理——改一下 requirements 只需要重跑最后几层，前面几十分钟的 CUDA 和 ROS2 安装全部命中缓存。

**第二，每一层只增不减。** 这一条很反直觉：如果你在某一层下载了一个 3GB 的文件，在**下一层**把它删掉，镜像还是会大 3GB。因为删除动作只是在新的一层里"标记为已删除"，底下那一层的数据还在。

这就解释了 Dockerfile 里到处都有的这个写法：

```dockerfile
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        build-essential \
        cmake \
        git \
    && rm -rf /var/lib/apt/lists/*
```

三件事必须写在**同一条 `RUN`** 里，用 `&&` 串起来：

- `apt-get update` 会下载一堆软件包索引，放在 `/var/lib/apt/lists/`；
- 装完之后这些索引就没用了；
- `rm -rf` 必须和它们在同一层，删除才真的能减小体积。

如果拆成三条 `RUN`，索引会永远留在镜像里，白白胖几百 MB。同理，编译完 librealsense 之后的 `rm -rf /tmp/librealsense-src` 也在同一条 `RUN` 里：

```dockerfile
RUN cd /tmp/librealsense-src && \
    mkdir build && cd build && \
    cmake .. ... && \
    make -j$(nproc) && \
    make install && \
    ldconfig && \
    cd /tmp && rm -rf /tmp/librealsense-src
```

> 还有一个原因：`apt-get update` 和 `apt-get install` 分开写会有隐患。假如 update 那层命中了三个月前的缓存，install 时拿到的就是三个月前的包索引，可能装到过时或者已经下架的版本。串在一起就没这个问题。

## 6.3 安装 Docker

### 6.3.1 装 Docker Engine

Ubuntu 22.04 上，用官方脚本最省事：

```bash
curl -fsSL https://get.docker.com | sudo bash
```

或者按官方文档一步步来（更推荐，出问题好排查），装完验证：

```bash
sudo docker run hello-world
```

看到一段欢迎文字就说明成功了。

### 6.3.2 免 sudo（强烈建议做）

默认情况下每条 docker 命令都要 `sudo`，很烦，而且会导致容器创建的文件属主是 root，后面很麻烦。把自己加进 `docker` 组：

```bash
sudo usermod -aG docker $USER
```

**然后必须重新登录一次**（注销再登录，或者直接重启）。只开个新终端是不够的，用户组是在登录时确定的。这一步很多人卡住，改完发现还是要 sudo，其实只是没重新登录。

验证：

```bash
docker run hello-world      # 不加 sudo 能跑就成功了
```

### 6.3.3 装 NVIDIA 容器运行时（要用 GPU 才需要）

容器默认是看不到显卡的。想在容器里用 CUDA，宿主机上要装 NVIDIA Container Toolkit：

```bash
# 添加源（具体命令以 NVIDIA 官方文档为准，会变）
sudo apt update
sudo apt install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

验证：

```bash
docker run --rm --gpus all nvidia/cuda:12.6.0-base-ubuntu22.04 nvidia-smi
```

如果能打印出你的显卡信息，就通了。

有一件事要先说清楚，不然容易困惑：

> **宿主机必须装 NVIDIA 驱动，但不需要装 CUDA Toolkit。**
>
> 驱动是内核层面的，容器共用宿主机内核，所以驱动必须在宿主机上。CUDA Toolkit 是用户空间的库，可以装在容器里——我们的 Dockerfile 第 3 段就在容器里装了 `cuda-toolkit-12-6`。
>
> 这也是 Docker 好用的地方之一：一台机器上可以同时跑需要 CUDA 11 和 CUDA 12 的两个容器，互不干扰。

## 6.4 第一条命令：把容器跑起来

### 6.4.1 起一个 Ubuntu 玩玩

```bash
docker run -it --rm ubuntu:22.04 /bin/bash
```

回车之后，你的命令行提示符会变成类似 `root@a1b2c3d4e5f6:/#`。**你现在在一个全新的 Ubuntu 22.04 里面了。**

试试：

```bash
cat /etc/os-release       # 看看是什么系统
ls /                      # 看看根目录
python3 --version         # 大概率会说没这个命令，因为是最小镜像
exit                      # 退出
```

这条命令拆开看：

| 部分 | 作用 |
| --- | --- |
| `docker run` | 从镜像创建并启动一个容器 |
| `-i` | 保持标准输入打开，你才能敲命令 |
| `-t` | 分配一个终端，提示符才好看 |
| `-it` | 上面两个的合写，几乎总是一起用 |
| `--rm` | **退出后自动删除这个容器**，玩一玩的时候加上，不然会攒一堆垃圾 |
| `ubuntu:22.04` | 用哪个镜像。冒号后面是**标签（tag）**，通常表示版本 |
| `/bin/bash` | 容器启动后执行什么命令 |

如果本地没有这个镜像，Docker 会自动去 Docker Hub 上拉。第一次会慢一点。

### 6.4.2 亲手验证"容器是一次性的"

这个实验值得花两分钟做一下，做完你就再也不会忘了：

```bash
# 起一个容器，创建一个文件
docker run -it --rm ubuntu:22.04 /bin/bash
root@xxx:/# echo "hello" > /test.txt
root@xxx:/# cat /test.txt          # hello
root@xxx:/# exit

# 再起一个
docker run -it --rm ubuntu:22.04 /bin/bash
root@yyy:/# cat /test.txt          # No such file or directory
```

文件没了。因为第二次是从**同一个镜像**起的**另一个全新容器**，第一个容器的可写层已经随着 `--rm` 一起删掉了。

现在把挂载加上再试一次：

```bash
mkdir ~/docker_test
docker run -it --rm -v ~/docker_test:/data ubuntu:22.04 /bin/bash
root@xxx:/# echo "hello" > /data/test.txt
root@xxx:/# exit

ls ~/docker_test        # test.txt 在这里！
```

`-v 宿主机路径:容器内路径` 就是挂载。这一次文件写在了宿主机上，容器删了也还在。

> `-v` 的宿主机路径**必须写绝对路径**（`~` 会被 shell 展开成绝对路径，所以可以用）。写相对路径 Docker 会把它当成"具名卷"，行为完全不同，这是个经典坑。

### 6.4.3 常用的容器管理命令

```bash
docker ps                 # 看正在运行的容器
docker ps -a              # 看所有容器，包括已经停止的
docker images             # 看本地有哪些镜像

docker stop <名字或ID>     # 停止容器
docker start <名字或ID>    # 重新启动一个停止的容器
docker rm <名字或ID>       # 删除容器
docker rmi <镜像名>        # 删除镜像

docker exec -it <名字> /bin/bash   # 进入一个正在运行的容器
docker logs <名字>                 # 看容器的输出
```

其中 `docker exec` 用得最多。日常开发是"容器一直开着，需要的时候 exec 进去"，而不是反复 run 新容器。

> `docker ps` 里的 `NAMES` 列，如果你没指定 `--name`，Docker 会随机起一个像 `epic_torvalds` 这样的名字。所以我们的 compose 里都写死了 `container_name`，找起来方便。不过这个做法配合 VS Code 的 Dev Containers 会有冲突，6.11.7 会说。

## 6.5 读懂 Dockerfile

现在来读我们真机上用的 `Dockerfile.ros2.gpu`。这份文件有两百多行，但结构很清楚：从一个空白的 Ubuntu 开始，一段一段地把 CUDA、ROS2、RealSense SDK、PyTorch 装进去。

**不要求你现在能写出来，能读懂就很好了。**

### 6.5.1 开头：从哪里开始

```dockerfile
FROM ubuntu:22.04

ENV DEBIAN_FRONTEND=noninteractive
WORKDIR /workspace
```

| 指令 | 作用 |
| --- | --- |
| `FROM` | **必须是第一条**（注释除外）。指定基础镜像，也就是"从什么开始" |
| `ENV` | 设置环境变量，会一直保留到容器运行时 |
| `WORKDIR` | 设置工作目录，相当于 `cd`。目录不存在会自动创建 |

`DEBIAN_FRONTEND=noninteractive` 这一行特别值得说。不加它的话，`apt install` 装到某些包（比如 `tzdata`）时会弹出交互式的时区选择菜单，等你按键。但构建过程里没人能按键，于是**构建就永远卡在那里**。

> 这是新手写 Dockerfile 第一次卡住的经典原因。看到构建停在一个奇怪的地方不动，先检查有没有这一行。

### 6.5.2 换源

```dockerfile
RUN rm -f /etc/apt/sources.list && \
    echo "deb http://archive.ubuntu.com/ubuntu jammy main restricted universe multiverse" > /etc/apt/sources.list && \
    ...
```

这一段是在重写 apt 的软件源列表。`jammy` 是 Ubuntu 22.04 的代号（每个版本都有一个，24.04 是 `noble`）。

后面 pip 那部分则统一加了清华源：

```dockerfile
-i https://pypi.tuna.tsinghua.edu.cn/simple
```

在国内不换源的话，构建时间可能从二十分钟变成两小时，甚至直接超时失败。这是个不起眼但性价比极高的优化。

### 6.5.3 装 CUDA

```dockerfile
RUN curl -fsSL https://developer.download.nvidia.com/.../cuda-keyring_1.1-1_all.deb -o cuda.deb && \
    dpkg -i cuda.deb && rm cuda.deb && \
    apt-get update && \
    apt-get install -y cuda-toolkit-12-6 && \
    rm -rf /var/lib/apt/lists/*

ENV CUDA_HOME=/usr/local/cuda
ENV PATH=/usr/local/cuda/bin:$PATH
ENV LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH
```

装完还要设三个环境变量，让系统知道去哪找 CUDA 的命令和库。`LD_LIBRARY_PATH` 是动态链接库的搜索路径，Linux 下最常见的"库找不到"报错基本都和它有关。

> 提醒一下：`cuda-toolkit-12-6` 这个包非常大，装完镜像会胖好几个 GB，构建也要不少时间。第一次构建建议找个网络好的时候，泡杯茶等着。后面因为有层缓存，只要不动这一段就不会重装。当然在确定版的情况下可以直接通过小组分发的本地安装包安装减少网络故障风险。

### 6.5.4 装 ROS2

```dockerfile
RUN curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key \
    -o /usr/share/keyrings/ros-archive-keyring.gpg

RUN echo "deb [arch=$(dpkg --print-architecture) \
signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] \
http://packages.ros.org/ros2/ubuntu \
$(. /etc/os-release && echo $UBUNTU_CODENAME) main" \
> /etc/apt/sources.list.d/ros2.list
```

这两段在做的事：先下载 ROS 官方的 GPG 签名密钥，再往源列表里加一行 ROS2 的仓库地址。签名密钥是用来验证下载的包没被篡改的，不加的话 apt 会拒绝安装。

里面有两个 shell 小技巧：

- `$(dpkg --print-architecture)` 自动获取 CPU 架构（x86 上是 `amd64`，Jetson 上是 `arm64`）；
- `$(. /etc/os-release && echo $UBUNTU_CODENAME)` 自动获取系统代号（`jammy`）。

这样同一份 Dockerfile 在不同架构上都能用，不用手动改。

然后是安装：

```dockerfile
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        ros-humble-desktop-full \
        python3-colcon-common-extensions \
        ...
ENV ROS_DISTRO=humble
```

`--no-install-recommends` 表示只装必需的依赖，不装"推荐但非必需"的。能省下相当可观的体积。

### 6.5.5 从源码编译 RealSense SDK

```dockerfile
COPY docker/docker_deps/librealsense-2.56.4 /tmp/librealsense-src

RUN cd /tmp/librealsense-src && \
    mkdir build && cd build && \
    cmake .. \
        -DCMAKE_BUILD_TYPE=Release \
        -DFORCE_RSUSB_BACKEND=ON \
        -DBUILD_EXAMPLES=false \
        -DBUILD_PYTHON_BINDINGS=true \
        ... && \
    make -j$(nproc) && \
    make install && \
    ldconfig && \
    cd /tmp && rm -rf /tmp/librealsense-src
```

这一段有几个点值得学：

**`COPY` 指令**：把宿主机上的文件复制进镜像。语法是 `COPY 宿主机路径 容器内路径`。

宿主机路径是**相对于构建上下文（build context）**的，不是相对于 Dockerfile。这里写 `docker/docker_deps/...`，是因为 compose 里指定了 `context: ..`（项目根目录）。这个概念下一节还会展开说，它是新手最容易搞混的地方之一。

**为什么用本地源码而不是 `git clone`**：注释里写了"锁死 v2.56.4"。原因有两个——一是版本确定，不会因为上游更新而某天突然构建失败；二是**赛场没网也能构建**。这个思路在下面装 PyTorch 时还会再出现一次。

**`make -j$(nproc)`**：`nproc` 返回 CPU 核心数，`-j` 是并行编译的任务数。这样能吃满所有核心，编译快很多。

**`ldconfig`**：刷新动态链接库缓存。装完 `.so` 库不跑这个，程序运行时会说找不到库。

### 6.5.6 ARG 与显卡分支

这一段是我们这份 Dockerfile 里最有意思的设计：

```dockerfile
ARG GPU_SERIES=50

COPY docker/docker_deps/whl /tmp/whl

RUN if [ "$GPU_SERIES" = "50" ]; then \
        echo "Install local cu128"; \
        pip3 install --no-cache-dir --no-index \
        --find-links=/tmp/whl/50 \
        torch torchvision torchaudio ; \
    else \
        echo "Install local cu126"; \
        pip3 install --no-cache-dir --no-index \
        --find-links=/tmp/whl/40 \
        torch torchvision torchaudio ; \
    fi
```

**`ARG` 和 `ENV` 的区别**是个高频考点：

| | `ARG` | `ENV` |
| --- | --- | --- |
| 生效阶段 | **只在构建时** | 构建时 + **容器运行时** |
| 能否从外部传入 | 能（`--build-arg`） | 不能直接传，但 compose 的 `environment` 可以设 |
| 容器里能看到吗 | 看不到 | 能，`echo $VAR` 就有 |

这里用 `ARG` 是对的：显卡型号只影响"构建时装哪个版本的 PyTorch"，程序跑起来之后不需要这个变量。

**为什么要分支**：40 系显卡（Ada 架构）和 50 系（Blackwell 架构）需要不同 CUDA 版本编译的 PyTorch。装错了的表现是——`import torch` 不报错，`torch.cuda.is_available()` 返回 `True`，但一跑推理就报：

```text
no kernel image is available for execution on the device
```

或者更直白的那句：

```text
NVIDIA GeForce RTX 5080 Laptop GPU with CUDA capability sm_120 is not compatible
```

这个报错第一次见很难联想到是版本问题——显卡明明认出来了，怎么会不兼容？

说说这个分支是怎么来的。开发机是 RTX 5080（Blackwell 架构，计算能力 `sm_120`），刚拿到手的时候，PyTorch 的稳定版还没有合入 Blackwell 的指令集，只能装开发预览版：

```bash
pip install --pre torch torchvision torchaudio \
    --index-url https://download.pytorch.org/whl/nightly/cu128
```

而队里其他人用的是 40 系，装 nightly 反而可能出别的问题，稳定版的 cu126 就够了。于是干脆把两套 whl 都下下来放进 `docker_deps/whl/40` 和 `docker_deps/whl/50`，构建时按 `GPU_SERIES` 选一套装。

> 这里有个更一般的教训：**买最新的硬件，就要有替上游生态填坑的心理准备**。算力是真香，但前沿硬件撞上旧版软件生态的南墙也是真蛋疼。写这份 Dockerfile 的一大半时间都花在这上面了。

**`--no-index --find-links=/tmp/whl/50` 是精髓**：

- `--no-index` = 不要联网去 PyPI 找；
- `--find-links=某目录` = 就从这个本地目录里找。

也就是说，PyTorch 那几个 GB 的安装包是**提前下载好放在项目里的**，构建时完全离线安装。比赛现场断网也能重新构建环境。

> 这个思路叫"离线依赖固化"，代价是仓库会变得很大（whl 文件通常要用 Git LFS 管理），但换来的确定性对比赛来说非常值。

### 6.5.7 那两遍 numpy 是怎么回事

Dockerfile 里 numpy 被安装了**三次**，中间还删过一次：

```dockerfile
# 第一次：先物理删掉系统自带的
RUN rm -rf /usr/lib/python3/dist-packages/sympy* && \
    rm -rf /usr/lib/python3/dist-packages/numpy* && \
    rm -rf /usr/lib/python3/dist-packages/opencv*

# 第二次：锁定版本
RUN pip3 install --no-cache-dir numpy==1.26.4 ...

# ...装完 requirements.txt 之后...

# 第三次：再锁一遍
RUN pip3 install --force-reinstall \
    numpy==1.26.4 \
    --no-deps \
    ...
```

看起来很啰嗦，但每一步都有血泪：

**为什么要先 `rm -rf`**：`apt` 装的 Python 包在 `/usr/lib/python3/dist-packages/`，`pip` 装的在 `/usr/local/lib/python3.10/dist-packages/`。两套系统各管各的，pip 卸载不掉 apt 装的包。当两边都有 numpy 时，`import numpy` 拿到哪个取决于路径顺序，玄学得很。直接把 apt 那份删掉最干脆。

**为什么最后还要再装一遍**：因为中间 `pip install -r requirements.txt` 时，某个包（很可能是 ultralytics 或 torch 的某个依赖）会说"我需要 numpy>=2.0"，然后**悄悄把你锁好的 1.26.4 升级掉**。等你发现的时候，报错信息通常是那句著名的：

```text
A module that was compiled using NumPy 1.x cannot be run in NumPy 2.x
```

所以最后要用 `--force-reinstall --no-deps` 强制按回去。`--no-deps` 表示"只装它自己，不要动它的依赖"，避免又引发一轮连锁升级。

> 这一段是很典型的工程现实：不好看，但它能跑，而且每一行都对应一个踩过的坑。你以后写自己的 Dockerfile 也会长出这种"疤痕"，这很正常。

顺便说一句，如果你去数这份 Dockerfile 的段落编号会发现，第 10 段后面跟着的注释写的是"[阶段 8]"。这是我改了好几版之后忘了同步注释留下的，不影响功能，但确实是我懒了。看到编号对不上不用怀疑自己读错了。

还有一行看起来很莫名其妙，其实也是踩出来的：

```dockerfile
# 4. 再次设置环境变量，确保 NVRTC 不会找不到库
ENV LD_LIBRARY_PATH=/usr/local/lib/python3.10/dist-packages/nvidia/cuda_nvrtc/lib:$LD_LIBRARY_PATH
```

前面第 3 段明明已经设过一次 `LD_LIBRARY_PATH` 了，为什么还要再设一次、而且路径这么长？

因为 PyTorch 在运行时会**动态编译 CUDA kernel**，这个活儿由 NVRTC（NVIDIA Runtime Compilation）来做。而 pip 装的 PyTorch 自带了一套 NVIDIA 库，藏在 `dist-packages/nvidia/` 底下——它不在系统的标准库路径里。找不到的时候报错长这样：

```text
nvrtc: error: failed to open libnvrtc-builtins.so.13.0
```

这个报错完全看不出和 pip 装包有什么关系，第一次遇到查了很久。解决办法就是把这个藏起来的路径手动加进 `LD_LIBRARY_PATH`。

> 记一个通用规律：Linux 下所有"库找不到"的报错，八成都能靠 `LD_LIBRARY_PATH` 或 `ldconfig` 解决。看到 `.so` 开头结尾的报错，先往这两个方向想。

### 6.5.8 收尾：用户与权限

```dockerfile
RUN useradd -m -u 1000 -s /bin/bash developer && \
    echo "developer ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers && \
    ...
USER developer
WORKDIR /home/developer
```

容器默认以 **root** 身份运行。这会带来一个很烦的问题：**容器在挂载目录里创建的文件，属主是 root**。你回到宿主机想改这个文件，发现要 `sudo` 才行；`git` 也可能报权限错误。

解决办法就是在容器里建一个普通用户，并让它的 **UID 等于 1000**。Linux 判断文件属主看的是 UID 数字，不是用户名。而 Ubuntu 上第一个创建的用户 UID 正好是 1000——也就是你自己。所以容器里的 `developer`(1000) 创建的文件，在宿主机看来就是你创建的，权限刚刚好。

可以用 `id -u` 确认你自己的 UID 是不是 1000。

`USER developer` 之后的所有指令，以及容器启动后的默认身份，都变成 developer 了。

接着是相机权限：

```dockerfile
RUN mkdir -p /etc/udev/rules.d && \
    echo 'SUBSYSTEM=="usb", ATTRS{idVendor}=="8086", MODE="0666"' > /etc/udev/rules.d/99-realsense-libusb.rules

RUN usermod -aG video developer && usermod -aG plugdev developer
```

`8086` 是 Intel 的 USB 厂商 ID（D435i 是 Intel 的产品），`MODE="0666"` 表示所有用户都能读写这个设备。再把 developer 加进 `video` 和 `plugdev` 组。不做这一步，容器里会出现"能看到相机但打不开"的情况。

最后是 `.bashrc`：

```dockerfile
RUN echo "source /opt/ros/humble/setup.bash" >> ~/.bashrc && \
    echo "if [ -f ~/ros2_ws/install/setup.bash ]; then source ~/ros2_ws/install/setup.bash; fi" >> ~/.bashrc && \
    echo "export ROS_DOMAIN_ID=42" >> ~/.bashrc && \
    echo "export PYTHONPATH=/ros2_vision_project:\$PYTHONPATH" >> ~/.bashrc

CMD ["/bin/bash"]
```

把 ROS2 的环境变量脚本写进 `.bashrc`，这样每次 `docker exec` 进来都自动 source 好了，不用手动敲。**开箱即用**这一点在排错时和赛场上很重要，紧张的时候少一步就少一个出错机会。

注意 `\$PYTHONPATH` 前面那个反斜杠：这里要写进文件的是字面量 `$PYTHONPATH`，不转义的话会在构建时就被展开成当时的值。

**`CMD` 和 `RUN` 的区别**也是个常见困惑：

| | `RUN` | `CMD` |
| --- | --- | --- |
| 什么时候执行 | **构建镜像时** | **容器启动时** |
| 能写几条 | 多少条都行 | 只有最后一条生效 |
| 作用 | 装东西、改配置 | 指定容器默认跑什么 |

`CMD ["/bin/bash"]` 的意思是：不指定命令的话，容器启动后就开个 bash。

## 6.6 构建与运行

Dockerfile 写好了，怎么变成镜像：

```bash
docker build -t 镜像名:标签 -f Dockerfile路径 构建上下文路径
```

比如：

```bash
docker build -t yolov8-d435i:ros2-gpu-latest -f docker/Dockerfile.ros2.gpu .
```

### 6.6.1 构建上下文是什么

最后那个 `.` 叫**构建上下文（build context）**，它是新手最容易搞混的东西，值得单独说。

构建开始时，Docker 会把这个目录下的**所有文件**打包发给 Docker 引擎。`COPY` 指令能复制的，只有这个范围内的文件。

```text
   docker build ... 上下文=项目根目录

   rc2026_vision/          ← 上下文边界，COPY 只能看到这里面的东西
     ├── docker/
     │    ├── Dockerfile.ros2.gpu
     │    ├── requirements.txt        ← COPY docker/requirements.txt ✓
     │    └── docker_deps/
     │         ├── whl/               ← COPY docker/docker_deps/whl ✓
     │         └── librealsense-2.56.4/
     └── src/

   ~/别的文件夹/xxx.txt                ← COPY 不到，超出上下文 ✗
```

两个直接后果：

1. **`COPY` 的源路径永远是相对上下文的**，不是相对 Dockerfile 的位置。我们的 Dockerfile 放在 `docker/` 下面，但 `COPY` 写的是 `docker/requirements.txt`，因为上下文是上一级目录。
2. **上下文越大，构建启动越慢**。如果项目里有几个 GB 的数据集或者 `.git`，每次构建都要先打包一遍。用 `.dockerignore` 文件排除掉（语法和 `.gitignore` 一样）。

### 6.6.2 现身说法：我的 compose 里三个服务是不一致的

对照一下我们 compose 文件里三个服务的 `build` 配置：

```yaml
  yolov8-ros2-cpu:
    build:
      context: .                              # ← 注意这里
      dockerfile: Dockerfile.ros2

  yolov8-ros2-gpu:
    build:
      context: ..                             # ← 和上面不一样
      dockerfile: docker/Dockerfile.ros2.gpu
```

CPU 版用的是 `.`（`docker/` 目录本身），GPU 版用的是 `..`（项目根目录）。

先说清楚原因：**这三个服务只有 GPU 版一直在维护**。CPU 版是最早期还没打通显卡透传时写的应急方案，Jetson 版是为了将来部署先占的位。后来实际开发全在 GPU 版上跑，那两个就再也没动过——目录结构调整的时候只同步了 GPU 版和 Jetson 版，CPU 版被落下了。

所以这份文件的真实状态是：**一个能用的，两个凑数的。** 我当时的想法是"三个都写好显得完整"，结果就是维护了个寂寞，还给后来读代码的人（也就是你们）制造了困惑。

这里想说两件事。

**第一，别学我，按需要写就行。** 你实际会用哪几种环境，就写哪几个服务。用不上的先不写，需要的时候再加，比留三个半死不活的强得多。没写的服务不会骗人，写了不维护的会。

**第二，这个不一致本身是个很好的例题。** 如果 CPU 版的 Dockerfile 里也写了 `COPY docker/requirements.txt`，它会去找 `docker/docker/requirements.txt`，然后报：

```text
COPY failed: file not found in build context
```

这个报错九成以上都是**上下文设置和 `COPY` 路径对不上**。以后你遇到它，第一反应应该是回去看 `context` 写的是什么，而不是去改 `COPY`。

（顺带一提，文件开头的 `version: '3.8'` 在新版 Compose 里已经不需要了，留着会有一条警告。这也是老写法的残留，删掉即可。）

## 6.7 docker compose：把一长串参数写进文件

### 6.7.1 为什么需要它

我们真机要跑的容器，如果用 `docker run` 写全，大概长这样：

```bash
docker run -it --name yolov8-ros2-gpu --hostname ros2-vision-detector-gpu \
  --network host --privileged --runtime nvidia --shm-size 8g \
  -e DISPLAY=$DISPLAY -e QT_X11_NO_MITSHM=1 -e ROS_DOMAIN_ID=42 \
  -e NVIDIA_VISIBLE_DEVICES=all -e NVIDIA_DRIVER_CAPABILITIES=all \
  -v $(pwd)/..:/ros2_vision_project -v /tmp/.X11-unix:/tmp/.X11-unix -v /dev:/dev \
  --device /dev/bus/usb:/dev/bus/usb \
  --restart unless-stopped -w /ros2_vision_project \
  yolov8-d435i:ros2-gpu-latest /bin/bash
```

没人想每天敲这个，也没人能记住。**Compose 就是把这一坨参数写进一个 YAML 文件**，然后：

```bash
docker compose -f docker-compose.ros2.yml up -d yolov8-ros2-gpu
```

### 6.7.2 逐段读我们的配置

```yaml
services:
  yolov8-ros2-gpu:
    build:
      context: ..
      dockerfile: docker/Dockerfile.ros2.gpu
      args:
        GPU_SERIES: ${GPU_SERIES:-40}
    image: yolov8-d435i:ros2-gpu-latest
    container_name: yolov8-ros2-gpu
    hostname: ros2-vision-detector-gpu
    shm_size: '8gb'
```

| 字段 | 作用 |
| --- | --- |
| `services` | 下面每一项是一个服务（一个容器）。我们这里有 cpu / gpu / jetson 三个 |
| `build.args` | 传给 Dockerfile 里 `ARG` 的值 |
| `image` | 构建出来的镜像叫什么名字 |
| `container_name` | 容器的固定名字，`docker exec` 时用得上 |
| `hostname` | 容器内部的主机名，就是提示符 `@` 后面那串 |
| `shm_size` | 共享内存大小 |

`${GPU_SERIES:-40}` 这个语法要说一下：**读环境变量 `GPU_SERIES`，如果没设置就用 `40`**。这样 40 系显卡的同学什么都不用改，50 系的同学在 `.env` 里写一行 `GPU_SERIES=50` 就行。

`shm_size` 也值得一提，它是我调 YOLO 训练时撞出来的。容器默认的共享内存只有 **64MB**，而 PyTorch 的 DataLoader 开多进程（`workers>0`）加载图片时要靠共享内存传数据，不够就会炸。麻烦的是它的报错完全看不出是内存问题：

```text
DataLoader worker (pid xxx) is killed by signal: Bus error
ConnectionResetError: [Errno 104] Connection reset by peer
```

我当时的现象是：训练第一个 epoch 跑到 100%、正要开始验证的那一刻整个卡死。看到 `ConnectionResetError` 第一反应是网络问题，结果查了半天跟网络毫无关系。

所以 GPU 版给了 8GB。Jetson 版给的是 4GB，注释里写了原因——Jetson 总共才 8GB 统一内存，给太多会挤掉别的。

### 6.7.3 三行必须加的挂载

```yaml
    volumes:
      - ../:/ros2_vision_project
      - /tmp/.X11-unix:/tmp/.X11-unix  # <--- 必须加上这一行！否则窗口弹不出来
      - /dev:/dev                      # <--- 必须加上这一行！否则相机找不到
```

原注释里那两个感叹号很真诚，我们逐条解释一下为什么：

**第一行**是代码挂载，6.2.2 讲过了。

**第二行是为了让 `cv2.imshow` 能弹出窗口。** X11 是 Linux 的图形系统，程序想画窗口，要通过 `/tmp/.X11-unix` 这个socket 和 X 服务器通信。容器里没有这个socket，`imshow` 就会报 `cannot connect to X server`。

光挂载还不够，宿主机上还要允许容器连接：

```bash
xhost +local:docker
```

**这条命令每次重启电脑都要重新执行**，是最高频的"明明昨天还好好的"来源。建议写进 `~/.bashrc` 一劳永逸。

**第三行是为了让容器看到相机。** USB 设备在 Linux 下表现为 `/dev/` 底下的文件，把整个 `/dev` 挂进去，容器就能看到所有硬件设备了。

> **这里必须招一下：设备相关的配置我写了三重，是冗余的。**
>
> `privileged: true` 已经给了容器访问所有设备的权限，严格来说 `/dev:/dev` 挂载和 `devices: /dev/bus/usb` 映射都不需要再写了。
>
> 当时的情况是相机死活打不开，我一边查资料一边往里加东西，加到某一次终于通了——然后就不敢删了，怕一删又坏。这是很典型的"能跑就别动"式调试，能理解，但不值得学：留下来的配置里有哪些是真正起作用的，我自己后来也说不清，只能靠事后推理。
>
> 正确的做法是通了之后**逐条删回去验证**，确认哪一条是必需的。你们写新配置的时候不用照抄这三条，先只加 `privileged: true` 试试，不行再往上加。

### 6.7.4 网络与权限

```yaml
    network_mode: host
    privileged: true
    runtime: nvidia
    stdin_open: true
    tty: true
```

| 字段 | 作用 | 注意 |
| --- | --- | --- |
| `network_mode: host` | 容器直接用宿主机的网络，不做隔离 | **ROS2 必须**，见下 |
| `privileged: true` | 特权模式，容器能访问所有设备 | 方便但不安全，仅限本地开发用 |
| `runtime: nvidia` | 用 NVIDIA 运行时，容器才能看到 GPU | 需要先装 nvidia-container-toolkit |
| `stdin_open: true` | 等价于 `docker run -i` | 和下面一起才能交互 |
| `tty: true` | 等价于 `docker run -t` | |

**为什么 ROS2 必须用 host 网络**：ROS2 的通信（DDS）靠 UDP 组播来自动发现网络里的其他节点。Docker 默认的桥接网络会把组播挡住，结果就是——容器里的节点和宿主机上的节点互相看不见，`ros2 topic list` 什么都没有。用 host 模式就没这个问题。

`ROS_DOMAIN_ID=42` 也和这个有关。同一个网络里的 ROS2 节点，只有 domain ID 相同才能互相通信。比赛时一个场地里好几支队伍，如果都用默认的 0，会互相收到对方的话题，场面非常混乱。所以每队约定一个自己的编号。

> 提醒：`ROS_DOMAIN_ID` 在三个地方都设了——compose 的 `environment`、Dockerfile 的 `.bashrc`、还有 `.env`。多处设置同一个变量时，优先级是 `docker run -e` / compose `environment` > Dockerfile `ENV`。以后改的时候记得三处一起改，不然会出现"我明明改了怎么没生效"。

### 6.7.5 GPU 的两种写法

```yaml
    runtime: nvidia

    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

这两段做的是同一件事：把 GPU 给容器用。`runtime: nvidia` 是老写法，`deploy.resources` 是新写法（对应 `docker run --gpus all`）。我们的配置两个都写了，属于双保险。

新写的话用 `deploy` 那一种就够了。

### 6.7.6 常用的 compose 命令

```bash
# 构建镜像（第一次，或者改了 Dockerfile 之后）
docker compose -f docker-compose.ros2.yml build yolov8-ros2-gpu

# 启动（-d 表示后台运行）
docker compose -f docker-compose.ros2.yml up -d yolov8-ros2-gpu

# 进去干活
docker exec -it yolov8-ros2-gpu /bin/bash

# 看日志
docker compose -f docker-compose.ros2.yml logs -f yolov8-ros2-gpu

# 停止并删除容器
docker compose -f docker-compose.ros2.yml down
```

因为一个 compose 文件里有三个服务（cpu/gpu/jetson），所以命令末尾要指定服务名，不然三个会一起启动。

> 老教程里写的是 `docker-compose`（中间有横杠），那是 Python 写的 v1 版本，已经不维护了。新版是 Docker 内置的 `docker compose`（空格）。功能基本一样，看到老写法不用慌。

## 6.8 .env：把会变的东西抽出来

### 6.8.1 它是干什么的

同一份 compose 文件，不同的人跑起来需要的参数不一样：显卡型号不同、模型路径不同、要不要保存视频不同。总不能每个人改一份 compose 再各自提交，那会天天冲突。

Docker Compose 会**自动读取同目录下的 `.env` 文件**，把里面的变量填进 `${...}` 占位符。我们仓库里给了一份 `env.example`：

```bash
# ===== GPU配置 =====
NVIDIA_VISIBLE_DEVICES=all
NVIDIA_DRIVER_CAPABILITIES=all

# ===== 模型配置 =====
MODEL_PATH=yolov8n.pt
CONFIDENCE_THRESHOLD=0.5
IOU_THRESHOLD=0.45
INFERENCE_DEVICE=cuda

# ===== 相机配置 =====
CAMERA_WIDTH=640
CAMERA_HEIGHT=480
CAMERA_FPS=30
ALIGN_DEPTH=true
```

用法就一步：

```bash
cp env.example .env
# 然后按自己的机器改 .env
```

### 6.8.2 为什么是 `env.example` 而不是直接给 `.env`

这是个很通用的工程惯例，值得记住：

```text
   env.example   ──▶  提交进 Git，是给人看的模板
        │
        │ cp
        ▼
      .env        ──▶  写进 .gitignore，不提交，每台机器一份
```

两个原因：

1. **每个人的机器不一样**。你的显卡是 50 系，队友是 40 系，提交上去会互相覆盖。
2. **`.env` 里迟早会出现密码和密钥**。数据库口令、API token 之类，一旦提交到 Git 就很难彻底删干净了（历史记录里还在）。养成 `.env` 永不提交的习惯，以后能救你一次。

请检查一下我们的 `.gitignore` 里有没有 `.env` 这一行，没有的话加上。

### 6.8.3 一个容易误会的点

`.env` 里的变量，**默认只是给 compose 文件里的 `${...}` 用的，不会自动变成容器内的环境变量**。

想让容器里也能 `echo $MODEL_PATH`，要在 compose 里显式写：

```yaml
    environment:
      - MODEL_PATH=${MODEL_PATH}
```

或者用 `env_file` 一次性全部导入：

```yaml
    env_file:
      - .env
```

我们现在的配置是手动列的（`DISPLAY`、`ROS_DOMAIN_ID` 那几个），所以 `env.example` 里的大部分变量其实还没有真正传进容器。如果后面代码要读这些配置，记得补上 `env_file`。

> 这也是为什么 `env.example` 写得很全但看起来"没用上"——它是照着未来的需求先规划好的。这没问题，只是要知道现状。

## 6.9 日常工作流

概念讲完了，来看实际每天怎么用。

### 6.9.1 第一次配置（大约一小时，主要在等）

```bash
# 1. 拉代码
git clone <项目地址>
cd rc2026_vision/docker

# 2. 准备环境变量
cp env.example .env
vim .env                 # 50 系显卡的话加一行 GPU_SERIES=50

# 3. 构建镜像（很慢，去干别的）
docker compose -f docker-compose.ros2.yml build yolov8-ros2-gpu

# 4. 允许图形界面
xhost +local:docker
```

### 6.9.2 每天开工

```bash
# 1. 启动容器（后台）
docker compose -f docker-compose.ros2.yml up -d yolov8-ros2-gpu

# 2. 允许图形界面（每次重启电脑后都要）
xhost +local:docker

# 3. 进去干活
docker exec -it yolov8-ros2-gpu /bin/bash

# 现在你在容器里了，ROS2 环境已经自动 source 好
developer@ros2-vision-detector-gpu:/ros2_vision_project$ ros2 topic list
```

在宿主机上用 VS Code 改代码，容器里立刻同步（因为挂载）。改完直接在容器里跑，**不需要重新构建**。

想开第二个终端？再执行一次第 3 步就行，可以开很多个。

### 6.9.3 收工

```bash
docker compose -f docker-compose.ros2.yml down
```

或者干脆不关，容器放着不占多少资源。

### 6.9.4 什么时候需要重新 build

这是最容易困惑的地方，列个表：

| 你改了什么 | 要重新 build 吗 |
| --- | --- |
| Python / C++ 源码 | **不用**，挂载的，直接生效 |
| 配置文件、模型权重（在挂载目录里） | **不用** |
| `Dockerfile` | **要** |
| `requirements.txt` | **要** |
| `docker-compose.yml` | 不用 build，但要 `down` 再 `up` |
| `.env` | 不用 build，但要 `down` 再 `up` |

还有一种情况：你在容器里临时 `pip install` 了一个包，当时能用，但容器重建后就没了。**临时装完记得回头补进 `requirements.txt`**，不然过两天换台机器又要重来一遍。这是团队协作里很常见的失误，不严重，但反复发生就很浪费时间。

### 6.9.5 磁盘满了怎么办

Docker 很吃磁盘。构建失败的中间层、旧镜像、停掉的容器都会堆积。

```bash
docker system df           # 看 Docker 占了多少空间
docker system prune        # 清理停止的容器、无用网络、悬空镜像
docker system prune -a     # 更狠，把所有没在用的镜像也删掉
```

> `-a` 要小心：它会删掉所有当前没有容器在用的镜像，包括你辛辛苦苦构建了一小时的那个。确认之后再敲。

顺便说一句，`docker images` 里显示的 SIZE 加起来通常会大于实际占用，因为镜像之间共享层。想知道真实占用看 `docker system df`，原理在 6.11.2。

## 6.10 把环境发给队友

镜像构建好了，怎么让队友也用上？三条路，从省事到费事排：

### 6.10.1 最好的办法：把 Dockerfile 交给 Git

代码仓库里有 `Dockerfile` 和 `docker-compose.yml`，队友 `git clone` 之后自己 `build` 一遍就行。这是最干净的做法——**环境即代码**，改了什么、为什么改，Git 历史里都有记录。

前提是网络够好、构建时间能接受。我们这份 Dockerfile 完整构建一次要一个多小时（CUDA 和 ROS2 都很大），第一次配环境泡杯茶等着就行。

### 6.10.2 网络不行的时候：直接传镜像

赛场或者宿舍网络不给力的时候，可以把构建好的镜像导出成文件传过去：

```bash
# 导出并压缩（-t 后面是镜像名:标签）
docker save yolov8-d435i:ros2-gpu-latest | gzip > ros2_gpu_v1.tar.gz

# 对方拿到之后
gunzip -c ros2_gpu_v1.tar.gz | docker load
```

`docker save` 会把镜像的所有层打包成一个 tar 文件。加上 `gzip` 通常能压掉三到五成体积，代价是压缩过程比较吃 CPU。

### 6.10.3 文件太大发不出去

我们的镜像压完还有 8GB 左右，微信和 QQ 都传不了这么大的单文件。用 Linux 自带的 `split` 切开：

```bash
# 切成每份 2000MB，文件名前缀 part_
split -b 2000M ros2_gpu_v1.tar.gz part_

# 得到 part_aa  part_ab  part_ac  part_ad ...
```

对方收齐之后一行命令合回来：

```bash
cat part_* > ros2_gpu_v1.tar.gz
```

`cat part_*` 会按文件名的字典序拼接，而 `split` 生成的后缀（`aa`、`ab`、`ac`…）刚好就是字典序，所以顺序不会错。合完建议校验一下再解压：

```bash
md5sum ros2_gpu_v1.tar.gz      # 两边对比一下这串数字
```

> 传之前记得先瘦身：容器里 `rm -rf ~/.cache/pip` 和 `apt-get clean`，能省下不少。当然，如果 Dockerfile 里已经老老实实写了 `--no-cache-dir` 和 `rm -rf /var/lib/apt/lists/*`，这一步基本就没什么可清的了——这也是 6.2.3 讲的那些写法的价值所在。

### 6.10.4 不推荐：docker commit

还有一种做法是进容器里手动装好东西，然后：

```bash
docker commit 容器名 新镜像名:标签
```

它会把容器当前的状态固化成一个新镜像。听起来很方便，但**强烈不建议用它来管理开发环境**，原因很实在：

- 你装了什么、改了什么，**没有任何记录**。三个月后想改一处，只能对着一个黑盒子发呆；
- 镜像会越滚越肥，因为每次 commit 都在原来的基础上又叠一层；
- 团队里没人能复现你的操作。

我干这事的代价就是执行 `docker commit` 打包几十 GB 的镜像时直接报了 `no space left on device`，然后是一整套连锁反应：清 pip 缓存、`docker system prune -f`、最后不得不做了个 Ubuntu Live USB，用 GParted 给根分区扩容。

> 一个通用建议：**给 Ubuntu 分区的时候，根分区至少留 200GB。** 玩 Docker + 深度学习，磁盘是消耗最快的资源，没有之一。

## 6.11 进阶话题：什么时候该拆，什么时候不该拆

这一节讲的东西现在用不上也没关系，但等你们开始管理多个项目的时候会回来找它。

### 6.11.1 镜像分层：Base + 分支

我们现在这份 Dockerfile 是"一条直线走到黑"——从 Ubuntu 开始，把 CUDA、ROS2、RealSense、PyTorch、YOLO 全部装进同一个镜像。这种叫**全能镜像（Full）**。

另一种做法是拆成一个底座加若干分支：

```text
              Dockerfile.base
              （Ubuntu + CUDA + ROS2 + RealSense）
                        │
                  build │ -t vision-base:v1
                        ▼
                 vision-base:v1
                    ╱         ╲
      FROM vision-base:v1   FROM vision-base:v1
            │                       │
   Dockerfile.train         Dockerfile.deploy
   （+ PyTorch/YOLO）        （+ ROS 业务包）
            │                       │
            ▼                       ▼
   vision-train:v1          vision-deploy:v1
```

**魔法全在 `FROM` 这一个词上。** `FROM ubuntu:22.04` 是从网上拉一个官方镜像开始，而 `FROM vision-base:v1` 是**从你本地已经构建好的镜像开始**。Docker 会直接把那个镜像的所有层搬过来当地基，继续往上盖。

所以有一条硬性要求：**必须先构建 base，后构建分支**。分支找不到"爹"会直接报错。一般会写个 `build.sh` 把顺序固定下来：

```bash
#!/bin/bash
set -e
docker build -f docker/Dockerfile.base   -t vision-base:v1   .
docker build -f docker/Dockerfile.train  -t vision-train:v1  .
docker build -f docker/Dockerfile.deploy -t vision-deploy:v1 .
```

### 6.11.2 为什么硬盘不会被占三份

这是我当初最想不通的地方：base 有 10GB，train 看起来 15GB，deploy 看起来 11GB，加起来 36GB？我这硬盘顶得住吗？

顶得住，因为**分层是共享的**。回到 6.2.3 讲的层：

```text
   vision-train:v1              vision-deploy:v1
   ┌──────────────┐             ┌──────────────┐
   │ PyTorch/YOLO │  5GB        │  ROS 业务包   │  1GB   ← 各自独有
   └──────┬───────┘             └───────┬──────┘
          └───────────┬─────────────────┘
                      ▼
          ┌───────────────────────┐
          │ Ubuntu+CUDA+ROS2+SDK  │  10GB       ← 硬盘上只有一份
          └───────────────────────┘

   实际占用 = 10 + 5 + 1 = 16GB，不是 36GB
```

Docker 用的是**联合文件系统（UnionFS）**，可以把镜像想成一叠透明胶片，叠起来看是完整的一个系统，但底下那张公共胶片物理上只存一份。所有基于同一个 base 的镜像都在读同一份数据。

`docker images` 里显示的 SIZE 是"叠起来看的总大小"，所以三个加起来会超过实际占用。想看真实占用用：

```bash
docker system df
```

### 6.11.3 但我们没这么做——因为不需要

分层听起来很专业，但**我们现在这个规模不该用它**。

拆分的收益是"让不同的人下载到更小的镜像"。只有当团队足够大、分工足够硬的时候才划算：五个人只搞 AI 完全不碰 ROS，另外五个人只搞底盘完全不碰 AI，这时候拆开才有意义。

我们的实际情况是：就那么几个人，而且同一个人今天训模型、明天调 ROS 节点。拆成两个镜像的结果是——训练那个里没有 `ros2` 命令，部署那个里没有 `torch`，来回切换非常难受。

还有一个必须澄清的误区（我当时就是这么以为的）：

> **两个分支镜像不能"合并"成一个 Full 版本。**
>
> `FROM base` 开出的两条分支是两个平行世界。Train 那个世界里根本没装 ROS2，Deploy 那个世界里根本没装 PyTorch。你用 compose 启动时，一个容器只能选一个镜像当身体。选了 Train，往里挂再多 ROS 代码，敲 `ros2` 也是 `command not found`——它身上就没这个软件。
>
> 想要真正的全能版，只能写一个把所有东西都装进去的 Dockerfile，也就是我们现在这份。

一句话结论，也是我们现在采用的策略：

**环境（镜像）大一统，代码（挂载）各自分离。**

### 6.11.4 代码目录要物理分离

镜像不用拆，但**代码目录一定要拆**。推荐的结构长这样：

```text
ros2_vision_project/          <-- Git 根目录
├── docker/                   <-- 构建中心：Dockerfile、compose、依赖
├── training_workspace/       <-- 训练区
│   ├── scripts/              <-- train_code.py 之类
│   ├── datasets/             <-- 数据集（几个 GB 到几十 GB）
│   └── runs/                 <-- 训练输出，写进 .gitignore
└── ros2_ws/                  <-- ROS2 工程区
    └── src/                  <-- 只放 ROS2 源码
```

然后在 compose 里分别挂进容器的不同位置：

```yaml
    volumes:
      - ../training_workspace:/workspace
      - ../ros2_ws:/home/developer/ros2_ws
```

**为什么必须分开，最实际的一条理由是 `colcon build`。** 它会递归扫描 `src/` 下面的所有目录去找包。如果你图省事把数据集也丢进 `src/`，那么每次编译它都要先把那 10GB 的图片挨个扫一遍，编译还没开始就已经卡了半分钟。

另外两个好处：

- **`.gitignore` 好写**：`training_workspace/datasets/`、`training_workspace/runs/`、`ros2_ws/build/`、`ros2_ws/install/` 各自成块，一目了然；
- **协作时互不打扰**：训练的同学只关心 `training_workspace`，写节点的同学只关心 `ros2_ws`，改动很少撞车。

> 还有个小坑顺便提一下。YOLO 的数据集 `.yaml` 里如果写相对路径，会因为你在哪个目录下敲的命令不同而报 `missing path`。解决办法是在训练脚本里用 `os.path.abspath(__file__)` 拿到脚本自己的位置，再拼出绝对路径传给 YOLO，这样在哪跑都不会错。

### 6.11.5 一个容器，挂多个工作空间

既然镜像只有一个，那能不能同时开着两个项目？可以，而且比想象中简单。

配合 VS Code 的 **Dev Containers** 插件，做法是：

- compose 文件单独放在一个"环境配置中心"目录里，只管容器长什么样；
- 每个代码工作空间各自有一份 `.devcontainer/devcontainer.json`，通过 `dockerComposeFile` 指向那个公共的 compose，并用 `workspaceFolder` 锁定自己的根目录。

然后用 VS Code 打开哪个文件夹，点"在容器中重新打开"，就自动连进去了。

这里有个我一开始理解错的地方：

> 你开两个 VS Code 窗口，看起来像是跑了两个容器，**其实物理上只有一个容器在运行**。VS Code 是在这一个容器里起了两个独立的 `vscode-server` 进程，分别服务两个窗口。因为 `workspaceFolder` 各自锁死了根目录，所以看起来互不干扰。

### 6.11.6 多工作空间时，别把 source 全塞进 .bashrc

这一条和我们 Dockerfile 现在的做法**是有冲突的**，得说清楚。

我们的 Dockerfile 里写了：

```dockerfile
RUN echo "source /opt/ros/humble/setup.bash" >> ~/.bashrc && \
    echo "if [ -f ~/ros2_ws/install/setup.bash ]; then source ~/ros2_ws/install/setup.bash; fi" >> ~/.bashrc
```

**单个工作空间的时候这样最省事**，进容器就能直接用，开箱即用。

但如果你在同一个容器里挂了两个甚至三个工作空间，把它们的 `install/setup.bash` 全写进 `~/.bashrc` 就会出事：环境变量（`AMENT_PREFIX_PATH`、`CMAKE_PREFIX_PATH` 这些）会互相叠加，同名的包不知道会用到哪个，编译和运行都可能出现"我明明改了这个包怎么没生效"的灵异现象。

更好的做法是**只把官方的 ROS 路径写进 `~/.bashrc`**，各工作空间的 setup 交给 VS Code 的终端配置：

```json
"terminal.integrated.profiles.linux": {
  "ros2_ws": {
    "path": "bash",
    "args": ["--init-file", "/home/developer/ros2_ws/install/setup.bash"]
  }
}
```

这样你打开哪个工作空间的窗口，终端就只加载那个工作空间的环境，隔离得很干净。

`devcontainer.json` 里还可以配 `postCreateCommand`，让容器起来之后自动跑一次 `rosdep update` 之类的初始化。

### 6.11.7 用 devcontainer 时，别写死 container_name

前面 6.4.3 和 6.7.2 我说过 `container_name` 写死了方便 `docker exec`。这在手动用 compose 的时候没问题，但**配合 Dev Containers 就会打架**：VS Code 重建容器时，旧的容器可能还占着那个名字，于是报：

```text
Conflict. The container name "/xxx" is already in use
```

临时解决：

```bash
docker rm -f 容器名
```

长期解决：用 devcontainer 的那套流程时，把 `container_name` 从 compose 里去掉，让 Docker 自动生成名字。反正你都用 VS Code 连进去了，也不需要手敲 `docker exec`。

两种用法各有各的写法，知道什么时候该用哪种就行。

## 6.12 常见问题排查表

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| `permission denied ... docker.sock` | 没加进 docker 组，或加了没重新登录 | `sudo usermod -aG docker $USER`，然后**注销重登** |
| 构建卡在某处不动，很久没输出 | 缺 `ENV DEBIAN_FRONTEND=noninteractive`，卡在交互提问 | 加上这一行；或者看是不是在下载大文件 |
| `COPY failed: file not found` | 构建上下文和 `COPY` 路径对不上 | 回去看 `context` 是什么，见 6.6.1 |
| 构建极慢 / 下载超时 | 没换国内源 | apt 换源，pip 加 `-i` 清华源 |
| 容器里 `nvidia-smi` 没有这个命令 | 没装 nvidia-container-toolkit，或没设 `runtime: nvidia` | 见 6.3.3 |
| `torch.cuda.is_available()` 是 False | 同上；或宿主机驱动版本太老 | 先在宿主机上 `nvidia-smi` 确认驱动正常 |
| `nvrtc: error: failed to open libnvrtc-builtins.so` | pip 装的 NVIDIA 库不在标准库路径里 | 把 `dist-packages/nvidia/cuda_nvrtc/lib` 加进 `LD_LIBRARY_PATH`，见 6.5.7 |
| 显卡功耗上不去，训练很慢 | Ubuntu 的 NVIDIA 驱动默认在 On-Demand 节能模式 | `nvidia-settings` → PRIME Profiles 切到 NVIDIA (Performance Mode)，**要重启** |
| `no kernel image is available` | PyTorch 版本和显卡架构不匹配 | 检查 `GPU_SERIES` 设对没有，见 6.5.6 |
| `imshow` 报 `cannot connect to X server` | 忘了 `xhost +local:docker` | 在**宿主机**上执行，每次重启都要 |
| 窗口还是弹不出来 | 少挂 `/tmp/.X11-unix`，或 `DISPLAY` 没传 | 检查 compose 的 volumes 和 environment |
| 容器里找不到相机 | `/dev` 没挂载，或权限不够 | 检查 volumes；容器里 `ls /dev/video*` 看看 |
| RealSense 能看到但打不开 | udev 规则或用户组问题 | 见 6.5.8；或临时用 root 进容器验证 |
| `ros2 topic list` 空的 | 网络模式不是 host，或 domain ID 不一致 | 见 6.7.4 |
| DataLoader 报 `Bus error` 或 `ConnectionResetError: [Errno 104]` | 共享内存不够（默认只有 64MB） | 调大 `shm_size`，见 6.7.2 |
| `Conflict. The container name is already in use` | 同名容器还占着（常见于 VS Code 重建容器） | `docker rm -f 容器名`；或去掉 `container_name`，见 6.11.7 |
| `colcon build` 启动特别慢 | 数据集之类的大目录被放进了 `src/` | 把数据集挪出去，见 6.11.4 |
| `docker save` / 构建时报 `no space left on device` | 根分区满了 | `docker system prune`；实在不够就扩容分区，见 6.10.4 |
| 宿主机上文件属主变成 root，改不了 | 容器以 root 运行 | 见 6.5.8 的 UID 1000 方案；临时用 `sudo chown -R $USER:$USER .` 救回来 |
| `import numpy` 报 1.x / 2.x 不兼容 | numpy 被某个依赖偷偷升级了 | 见 6.5.7，最后强制装回 1.26.4 |
| 磁盘空间不够 | 镜像和中间层堆积 | `docker system prune`，见 6.9.5 |
| 改了代码但容器里没变 | 挂载路径不对，或你改的不是挂载目录里的文件 | 容器里 `ls /ros2_vision_project` 确认一下 |

## 6.13 关键词与命令速查表

这一节是查的，不是背的。

### 6.13.1 Dockerfile 指令

| 指令 | 一句话说明 | 典型写法 |
| --- | --- | --- |
| `FROM` | 指定基础镜像，**必须是第一条** | `FROM ubuntu:22.04` |
| `RUN` | **构建时**执行命令，每条产生一层 | `RUN apt-get update && apt-get install -y vim` |
| `COPY` | 把宿主机文件复制进镜像，源路径相对**构建上下文** | `COPY docker/requirements.txt /tmp/` |
| `ADD` | 类似 `COPY`，还能自动解压和下载 URL。**一般用 `COPY` 就好**，行为更可预测 | `ADD x.tar.gz /tmp/` |
| `ENV` | 设环境变量，**构建时和运行时都在** | `ENV CUDA_HOME=/usr/local/cuda` |
| `ARG` | 构建参数，**只在构建时有效**，容器里看不到 | `ARG GPU_SERIES=50` |
| `WORKDIR` | 设置工作目录，相当于 `cd`，不存在会自动建 | `WORKDIR /workspace` |
| `USER` | 切换后续命令和容器运行时的身份 | `USER developer` |
| `CMD` | 容器**启动时**的默认命令，只有最后一条生效 | `CMD ["/bin/bash"]` |
| `ENTRYPOINT` | 和 `CMD` 类似但更"写死"，`CMD` 的内容会变成它的参数 | `ENTRYPOINT ["python3"]` |
| `EXPOSE` | 声明容器用了哪个端口（**只是文档，不会真的开放**） | `EXPOSE 8080` |
| `VOLUME` | 声明某个目录是数据卷 | `VOLUME /data` |
| `LABEL` | 给镜像加元信息（作者、版本等） | `LABEL maintainer="alg-team"` |

## 本章练习

1. 用 `docker run -it --rm ubuntu:22.04 /bin/bash` 起一个容器，在里面 `apt install vim`，退出后再起一个，确认 vim 没了。
2. 重做 6.4.2 的挂载实验，然后想一想：如果把容器里的挂载目录整个 `rm -rf` 掉，宿主机上的文件会怎样？（想清楚再动手，别在真项目上试）
3. 自己写一个最小的 Dockerfile：基于 `ubuntu:22.04`，装上 python3 和 opencv，`CMD` 设为进入 python3 交互环境。构建并跑起来。
4. 把上一题的 Dockerfile 故意拆成三条 `RUN`（update、install、rm 各一条），用 `docker images` 比较两次构建出来的镜像大小。
5. 在第 3 题的镜像里，`import cv2` 之后调用 `cv2.imshow` 显示一张图。走通"挂载 X11 + xhost"这一整套。
6. 读 `docker-compose.ros2.yml` 里的 Jetson 服务，列出它比 GPU 服务多了哪些 `devices`，并查一查这些 `/dev/nvhost-*` 是干什么的。
7. 把任意一个用到摄像头的 OpenCV 脚本放进挂载目录，在容器里跑起来，确认窗口能弹出、相机能打开。（提示：相机设备号在容器里可能和宿主机不一样，先 `ls /dev/video*` 确认）
8. 用 `docker save` 把你第 3 题构建的镜像导出，用 `split` 切成 100MB 一块，再 `cat` 合回来 `docker load`，全程走一遍。
9. 给项目写一个 `.dockerignore`，把 `.git`、模型权重、数据集排除掉，比较一下构建启动的速度差别。
10. 进阶：把你第 3 题的 Dockerfile 拆成 `Dockerfile.base`（装 python3）和 `Dockerfile.app`（`FROM` 你的 base，再装 opencv），构建之后用 `docker system df` 看看实际占用是不是小于两个镜像 SIZE 之和。

## 本章小结

这一章的核心其实就三句话：

```text
   Dockerfile ──build──▶ 镜像 ──run──▶ 容器
   （怎么做）            （做好了）    （正在跑）

   环境的东西  →  写进 Dockerfile，重新 build
   代码的东西  →  放进挂载目录，改完直接跑
   会变的参数  →  抽进 .env，每台机器一份
```

新手最容易搞混的三件事，如果你现在能分清楚，这一章就算到位了：

- **镜像 vs 容器**：镜像是只读的模板，容器是跑起来的实例。改容器不改镜像。
- **`ARG` vs `ENV`**：`ARG` 只在构建时有，`ENV` 运行时也有。
- **构建上下文**：`COPY` 只能看到上下文目录里的东西，路径相对上下文而不是 Dockerfile。

还有两条经验，比具体命令更值得带走：

- **能确定的东西就锁死**。锁 numpy 版本、锁 librealsense 版本、把 whl 提前下好，看起来啰嗦，换来的是"任何时候重新构建结果都一样"。赛场上这份确定性非常值钱。
- **不要在容器里改环境**。想装什么，回去改 Dockerfile 或 `requirements.txt`，重新构建。在容器里临时装的东西，下次一定会忘。
- **不确定的就先别写**。三个服务只维护得动一个，就只写一个；配置加了一堆终于通了，回头逐条删着验证一遍。留着不维护的东西，比缺东西更害人。

最后一句私货：这一章你会觉得琐碎，因为它讲的全是"让别的事情变简单"的事情。花一天把环境固定下来，换来的是后面几个月不用再为环境操心。这笔账很划算。
